walk paths

A walk and its path: an ordered list of steps, one concept each, that the learner can see and change. The module is abhyasa.journey.

A learner often wants to learn more than one concept. “I want to learn how LLMs work” needs tokenizers, embeddings, attention, transformers and more, in a given order. A walk keeps that goal and that order on the learning shelf.

The planner (one model call) proposes the steps. It uses the concepts on the shelf when they fit. It makes new concepts for the topics that the shelf does not have. Then the learner can change the path: move, skip, mark as known, add and split steps.

A walk keeps the outcome of each check on its step, and walk_state counts them. A concept that the learner learns anywhere is known in each walk that has it. An old walk with no mode (a path, from before 0.0.16) becomes a topic walk once, in the background at the start of the app, with its progress (walk_path).

The document

A walk is one vault document of kind journey. Its meta has the goal, a title, a subject, and the steps. Each step has a slug, a status (todo, known or skip) and the reason that it is in the path.

The source map

A goal can name its sources, such as course22p2 and fastbook. The Start box files them as chips. chip_docs gives the documents of each chip that is in the vault: a folder, a repo, a GitHub repo or one vault document. source_map gives the planner, for each chip, its root and up to 40 documents, each as its short title and its first heading. So the plan can name the document of each step.

Walks

A walk from a source has mode='walk'. It is the reading path: one step for each idea, in reading order. Each step has the passage to read (read) and the check to do (check).

_check picks the check of one concept. It uses the stats and the profile of the learner, as Tutor.ask_on does. abhyasa runs no code: when the chosen way is code, the check kind is notebook, and the step runs in Leela. On a tool walk (tool=True), or for a step that needs a library, its reason says so. A step that the plan marks hands='notebook' gets it too.

short_check gives a short-answer check in a text way. A walk uses it when a demo or an order check has no card. The way comes from the text ways of the concept, or from all text ways. A code way is not in the list, because its check is a code task.

A walk has a most number of steps

A long source, such as a docs site, can have 60 ideas or more. A walk of that length is too long to finish, and each step costs model calls for its note and its check. So a walk has at most val('walks.steps') steps (12 by default; you can change it on the Settings page). When a source has more ideas, main_steps asks the model one time to pick the main ideas, with the prompt walk.pick. You can change it on the Settings page. When the reply has fewer valid numbers, the first ideas that are not picked fill the walk in source order. The steps keep the order of the source, and a prerequisite that is picked comes before the idea that needs it. The pick happens when the walk is made, before any step writes a note or a check. The other ideas stay on the shelf as concepts. The walk keeps their slugs in more, so the plan can say how many more ideas the source has.

Your data

A course or a walk can keep folders of your own data in data, as a list of {path, note}. abhyasa does not file these folders and does not learn from them. The exercises run on them in Leela. data_row checks one folder, and keep_data adds it to a list. data_entries makes the data entries of a notebook spec: an upper-case name from the folder name, the path, and what, with the note and a short listing of the folder. with_data adds them to the entries of a step.

Change a step, read the rail

walk_step merges changes into one step and saves the walk. merge_journey merges changes into the fields of the walk, such as sitting. Both hold one lock for each walk id, so two requests on one walk do not lose a change. walk_state gives each step a dot for the rail: done (outcome solid), shaky (outcome fragile, gap or misconception), skipped, known, now (the first step with no outcome and the status todo) or todo.

The sections of a walk from a paper or a link follow the document: a new document or a new section name starts a section. A walk from a topic or a goal has no source document (source is empty). Its sections are the sections of the plan (the section of a step), so a passage from another document does not start a section, and “Section done” shows only at the end of a plan section.

Rabbit holes

A step can need an idea that you have not learned. For example, the scaling by √dk in a paper on attention needs gradients. These functions find what is missing, make a short side walk on it, and link the side walk back to the step.

needs lists the prereqs of a concept, then its gaps. A need is met at depth READY (3) or more, as in model.ready.

pick_way_down picks how to learn a missing idea:

  • walk: a side walk on the chain, at most walks.chain (4 by default) ideas. The chain is the unready prereqs, deepest first, then the idea.
  • session: a longer chain. It opens as its own walk.

The place that you used last

last_place says where Continue goes. It is the one function for the top bar, the card on Today and the card of a course. A place is a step of a walk that is not finished, or an open session with no walk. Each walk gives the time that you used it last: the idea that you were on (here, which the idea page writes), the newest idea that you read, or the start. A session gives the time of its last change. The newest place wins. A side walk counts as the step that opened it, so Continue goes back to the paper. Only the newest most walks are read. The step is the idea that you were on when it is not done, else the current step of the walk.

Open in Leela

Code with a library, tools and a code lookup are learned in Leela. abhyasa keeps only the small stdlib code check. So a walk can be marked as a tool walk (tool=True), and abhyasa shows a link that opens the walk, a step or a topic in Leela. abhyasa never calls Leela. It makes a path and a query. The learner’s browser opens the link on the Leela that runs on the same computer.

handoff makes the path and the query. read_handoff is the other side, for Leela. HANDOFF_CASES are the cases that both test suites run. They are in abhyasa.contract, which uses only the standard library, so Leela reads them with no abhyasa web code. This module gives the same names.

The link also has the vault key v: vault_key of the vault that abhyasa uses. Leela compares it with the key of its own vault. When the keys are not the same, the two apps use different vaults, and Leela tells you. A link with no v (from abhyasa 0.0.12) works as before.

These cases are shared. Leela runs the same list in its contract test. The last case has a vault key.
