# Plan: abhyasa as a Mac app with a Homebrew cask

Date: 25 October 2026. Status: plan only. Nothing here is built yet.

## Goal

Install abhyasa with `brew install --cask vedicreader/tap/abhyasa`. Open it from the Dock or with Spotlight. It works like
Sanketa: a signed, notarized app from a GitHub release, with a cask in `vedicreader/homebrew-tap`.

## Decision: a thin Swift app around the Python server

| option | for | against |
|---|---|---|
| Swift shell + `uv` (chosen) | Small signed surface. Same release flow as Sanketa. Native mic prompt, menu, Dock, hotkey. | First launch needs the network one time to build the Python environment. |
| py2app, as Leela | One self-contained bundle. | Needs a framework Python. Notarization needs a signature on every `.so`. Leela's build shows how much work this is. |
| Embedded python-build-standalone | No network on first launch. | Large bundle. You must sign every native library by hand. |

## How the app works

1. `Abhyasa.app` is SwiftUI. One window holds a `WKWebView`.
2. `Contents/Resources` holds a `uv` binary (signed), and abhyasa's `pyproject.toml` and `uv.lock` pinned to the release.
3. On launch, the supervisor runs `uv sync --frozen` into `~/Library/Application Support/abhyasa/env` when the lock changed.
   A first-run screen shows the progress. Later launches skip this step.
4. The supervisor picks a free loopback port and starts `abhyasa --port <port>`. It waits for `/health`, then loads the page.
5. When the app quits, the supervisor stops the server. A server crash shows a short message and a "Start again" button.
6. The vault is `~/.vishalakshi/vault.db`. Every other tool uses the same file. Settings: model, speech engine, vault path.

## Native parts

- Microphone: `NSMicrophoneUsageDescription`, and a `WKUIDelegate` that grants `getUserMedia` for the loopback origin only.
  The ⌥D, ⌥S and ⌥W keys keep working in the web view.
- Menu: New session (⌘N), Today, Graph, Search (⌘F), Add a source.
- A Dock badge with the number of reviews that are due, from `/health` or a small `/due.json` route.
- Later: a global hotkey (left-hand chord) that opens a review question in a small panel.
- An `abhyasa://concept/<slug>` URL scheme, so that Sanketa results open in the app. Sanketa's vault search now opens
  `http://127.0.0.1:5077/c/<slug>`. It changes to the URL scheme when the app exists.

## Where the code goes

`mac/` in the abhyasa repo: `Package.swift`, `Sources/Abhyasa/`, `Resources/Info.plist`, `entitlements.plist`, and a `Makefile`
copied from Sanketa's (`bundle`, `release`, `publish`, `cask`, the no-dry-run guards, `scripts/notarize.sh`). Same team ID and
Developer ID as Sanketa. Bundle id: `dev.vedicreader.abhyasa`.

## Release flow

1. Release the Python package first: CHANGELOG entry, `nbdev-prepare`, push, `nbdev-release-git`, `nbdev-pypi`.
2. In `mac/`: bump the version, copy the released `uv.lock`, then `make publish` (sign, notarize, staple, GitHub release).
3. `make cask` writes `Casks/abhyasa.rb` in `homebrew-tap` with the new version and SHA. Commit and push the tap.

The cask follows `sanketa.rb`: `depends_on arch: :arm64`, `depends_on macos: :tahoe`, `uninstall quit:`, and `zap trash:` for
`~/Library/Application Support/abhyasa`. It does not delete the vault.

## Steps

1. Spike: a SwiftUI window with a web view on the running server. Check the mic grant and the keys.
2. Supervisor: `uv sync --frozen`, port pick, health wait, restart, quit.
3. First-run screen and settings.
4. Menu, Dock badge, URL scheme.
5. Makefile and notarization, copied from Sanketa. A local unsigned build first.
6. Cask and tap. Test `brew install --cask` on this Mac.

## Open questions for the user

- Is one network fetch on first launch acceptable? If not, use the embedded Python option.
- Must the app also run the ramabana extension setup (write `~/.config/ramabana/extensions/abhyasa.py`)? The plan says no.
  The app does not change the configuration of other tools without asking.
