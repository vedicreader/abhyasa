Show an idea: the screen guide, the demos and the talks.

This module holds the ways that abhyasa shows an idea. It imports from all the modules above it. It has three parts:

  • The screen guide: the board that the tutor draws over a page when you press Explain, its checks, and its three tiers of sources.
  • Demos: the interactive figures and the 3D explainers from rupaka, with the ladder of lessons after a miss.
  • Talks: a walk made into slides for a group, with the questions for the room.

Import the modules that this module uses. The heavy ones load inside the functions that need them, so the import stays light.

The screen guide

The screen guide: “I don’t get X”, answered with a board that the tutor draws over the page.

The learner looks at a walk step, a concept or a video, and says “I don’t get alpha bar”. The guide answers on the page, as a teacher does at a whiteboard. It circles the term, draws an arrow to a label in the figure, moves the slider of the demo, and speaks one short line for each step.

This module is the part of the guide that has no web page:

  • the board language: a closed list of drawing commands, each tied to a thing on the page (an anchor), and the check of each line of the model’s reply;
  • the context: what the page shows, cleaned and cut to size;
  • the gate: the tutor answers at once when it is sure, else it looks in your vault, else on the web;
  • the guard: no secret and no personal data leaves the Mac in a model call or a web query.

The board language, its checks and the page context are in rupaka.board. The guide block serves the board, and rupaka’s board.js draws it.

Import the helpers. The model layer and ramabana load only on the first call, so the import stays light.

The board language

The board is in rupaka: rupaka.board has the language of 14 commands, the check of each line (check_line), the whole reply (parse_board), the page context (clean_context), the video cues and the stream (stream_board). Its docs give each command and each rule. This module imports these names, so from abhyasa.show import parse_board works. GUIDE_KINDS is the old name of rupaka’s KINDS.

The trust of a quote

A quote of a step stays only when it is word for word in its source. abhyasa has its own rule for “word for word”: abhyasa.sources.verbatim also reads past the lines of page data, the Markdown marks and the row numbers of view_file. rupaka’s default rule is plainer. So each call of parse_board and stream_board in this module passes verbatim.

from abhyasa.sources import verbatim

A quote of a source with Markdown marks stays with the rule of abhyasa. With the plain rule of rupaka, it drops:

Labels inside a figure

A figure is an image. Its labels (the “a” and “b” on the sides of a triangle) are not in the page text. The guide finds them once with a vision call and keeps their boxes for that figure. It keeps only the boxes, never the image.

source

figure_labels

def figure_labels(
    vision, img:bytes, alt:str=''
)->dict | None:

The labels in the figure image img, as text to a box from 0 to 1000, from the reply of vision(prompt, img, sp). None when the call fails or its reply is not JSON, so that no one keeps an empty result. A key in alt is masked here; vision_ask guards the full prompt for the model of its route.

FigureCache keeps the boxes in one JSON file, by the SHA-1 of the image bytes. A figure that changes gets a new key.

source

FigureCache

def FigureCache(
    path, most:int=500, empty_ttl:float=86400.0
):

The label boxes of each figure, by the SHA-1 of its bytes, in the JSON file path. It keeps at most most figures. An empty result is kept for empty_ttl seconds, and only when some figure in the file has labels: before that, an empty reply can come from a route that lost the picture, and the next post must ask again.

An empty result is not kept while no figure has labels. After one figure has labels, an empty result is kept, but only for empty_ttl seconds:

import tempfile
fc = FigureCache(Path(tempfile.mkdtemp())/'figs.json', empty_ttl=60)
test_eq((fc.put('k1', {}), fc.get('k1')), (False, None))
test_eq((fc.put('k2', {'a': [1, 2, 3, 4]}), fc.put('k1', {}), fc.get('k1'), fc.get('k2')), (True, True, {}, {'a': [1, 2, 3, 4]}))
d = fc._all(); d['k1']['at'] -= 61; fc.path.write_text(json.dumps(d))
test_eq(fc.get('k1'), None)   # too old: the next post asks again

The vision call goes through ramabana, on the job guide_vision: compose puts the image before the text, and the call runs only when the routed model takes a picture (accepts) and its route sends one (keeps_images). vision_why says in one line why the call does not run. The prompt and the system prompt pass guard for the model of each route, so a model on this Mac gets the text as it is. With a test model that has no routing, the call is a plain text call that passes guard for a hosted model, so a Fake can answer it.

rishi’s remote one-shot makes its message only from the parts that are dicts. So the raw image bytes and the text of compose do not get to the model, and the model answers a prompt with no figure. keeps_images finds this with no model call: it gives the same parts to the message code of the route and looks for the picture.

The prompt

The system text says the rules of the board. The parts that change (the question, the page, the sources) come last in the request, so a provider’s prompt cache can keep the system text.

Step 1 marks the asked part with a circle or a box, and has at most one point for context. So a point never takes the place of the main mark.

test_eq(('mark the part that the learner asked about with a circle or a box' in GUIDE_SP, 'at most one point in step 1' in GUIDE_SP,
         'Point at them when you name them' in GUIDE_SP), (True, True, False))

A sketch is for a figure only, and a picture of an idea goes in the side panel: a diagram that the learner asks for is a panel, not marks on the passage. A question about the answer starts with the problem in it, and the final answer waits while tries are left:

test_eq(('only on a figure anchor' in GUIDE_SP, 'Never use sketch for a picture of an idea' in GUIDE_SP, 'the panel draws one' in GUIDE_SP), (True, True, True))
test_eq(('Step 1 names the problem in their answer' in GUIDE_SP, 'stop before the final answer' in GUIDE_SP,
         'give the full worked solution' in GUIDE_SP, 'Step 2 explains' in GUIDE_SP), (True, True, True, False))
ex = [json.loads(l) for l in GUIDE_SP.split('An example reply', 1)[1].splitlines() if l.startswith('{')]

A formula gets a day-to-day example in the spoken lines. Each line is one short sentence, and a code name is said as words:

A process is a side panel with numbered rows. The answer of a row is in to, and a head names no count. A panel has one shape: a table (which alone can have column names), a chain, a flow of boxes, a faded example, a wrong idea, or three stages. rupaka drops a line of another shape, so the prompt names each shape and when to use it. The title is the small line and the head is the big heading, so the prompt says which is which:

The explainer video

A concept can have one explainer video from YouTube. The tutor finds one with fossick’s search_yt, or you paste a link. fossick reads the transcript and its timed cues (read_yt). The vault files the transcript as a document (Vault.youtube), and the cues go into its meta. The concept keeps the video in its provenance as src='video'. A video is a source like any other: a quote from it must be word for word, and the board names it as video, with its channel and title.

abhyasa reads no transcript itself. The id comes from video_id of rupaka.board, which refuses a link that names no video.

find_explainer searches YouTube for an idea. The query passes safe_query, as each web query that leaves the Mac does. It takes the first result that is a video of 1 to 60 minutes.

A board as a hint

On a page with an open check (the anchor check), a board counts as one hint on the check only when it is about the check (on_check): the learner showed the check with the pointer, or named it (“check”, “question”, “answer”, “hint”, “quiz”), or the main words of the question are words of the check (two of them, or all when there are fewer). The guide decides this before it asks, so it can tell the learner first. A board that does not count may not touch the check: the request says so (OFF_CHECK), and a stroke on the check drops. Then the learner keeps the hints for a real hint.

When the page sends the learner’s last try (the anchor try), a question about the try counts too: one that names the gaps, the try, a mistake, an error, what is wrong or the feedback (TRY_ASK), or a pointer on the try. Then the request says so (ON_TRY), and the model follows the rule for a question about an answer. A board that does not count gets no try.

The three tiers

The guide asks in up to three tiers, and the board shows which one it used:

  1. tutor: the page alone. When the model says that it is sure (sure of SURE or more), the board draws at once. The passage on the page is source 1, so a quote from it shows as your source.
  2. vault: else the guide searches your sources (ground) and asks again with the passages that it finds.
  3. web: else, when research is on, it searches the web, reads the pages, and takes a passage that is word for word in the page (research.pick_passage, the gate of research). Then it asks one last time with that passage. The page goes into your vault, linked to the concept. The page says so at the end of the board, with Undo (unsave).

When no tier is sure, the best board so far shows, in the tutor’s own words.

Never caught unaware

The learner must always know what the guide does now, and where the text goes. So before each step of its work, explain sends a state event to on_state. The guide route sends each one to the page as it comes, and the page shows it in one line, the guide bar. The Mac overlay reads the same events. This is the one shape:

{"wait": "<one STE sentence>", "state": "reading" | "asking" | "searching" | "saving" | "drawing",
 "model": "<model label>", "where": "on this Mac" | "hosted", "who": "<company of a hosted model, or ''>",
 "query": "<the web query word for word, only for searching>", "sources": <count of vault passages or web pages that go to the model>}

wait is always a full sentence, because an old page reads only wait. A field that does not apply is not in the event. explain sends asking, searching, reading and saving. The page itself shows reading for its own read, and drawing when the first step draws, so the route never sends a line that covers the board.

When the guide files a web page in the vault, explain sends {"saved": {...}} with the document and the concept link. The route gives the page {"saved": {"title", "url", "undo"}}, where undo is the POST route that takes the page and its link away again (unsave).

The board as it comes

stream_board is in rupaka.board. explain passes abhyasa’s verbatim to it.

A board takes some seconds to write. So the tutor tier streams it, and the first step draws while the model writes the next one. stream_board reads the reply as it comes. When a new line is in, it reads the whole lines so far again with parse_board, so the rules are the same as for a whole reply. When the header says sure of SURE or more, on_step(step, k) gets each step as soon as its spoken line and its first mark are in, and again each time it gets more strokes: so the first mark does not wait for the rest of the step (the rows of a side panel) or for the next step. The page adds the strokes that it does not have yet. A step that is not sure, or a reply with no header, sends nothing, and the guide goes on to the vault and the web as before. The board that stream_board returns is the truth: its first steps are the steps that went to on_step.

When the stream breaks after a step went out, the board keeps the whole lines that came, so the page does not lose what it shows.

The learner can stop: a newer question, Esc, or a closed tab. Then the guide route sets the threading.Event stop. stream_board reads no more chunks and closes the stream. So the model call ends at once, and the next question does not wait for the backend.

Chunked is a test model that streams its reply in chunks of 7 characters. It writes each chunk in events, and the test writes each step there too, so the order of the events shows when each step went out.

class Chunked(Fake):
    "A `Fake` that can stream: `stream(prompt, sp)` gives its reply in chunks of 7 characters, and notes each one in `events`."
    def __init__(self, *a, **kw): super().__init__(*a, **kw); self.events = []
    def stream(self, p, sp=''):
        out = self(p, sp)
        for i in range(0, len(out), 7): self.events.append('chunk'); yield out[i:i + 7]

three = '\n'.join(json.dumps(o) for o in [dict(op='v', n=1, sure=0.9), dict(op='step', say='Alpha bar t is the share that is left.'),

The board in the page

rupaka’s board.js (rupaka.board.assets()) draws the checked board. The app serves it at /assets/board.js. It takes its numbers from Clicky (github.com/farzaa/clicky, MIT):

  • The pointer. A small triangle in the board ink flies to each mark on a quadratic arc. The arc lifts by min(d * 0.2, 80) px, the flight takes clamp(d / 800, 0.6, 1.4) s, and the easing is smoothstep. The pointer turns to its path and grows to 1.3x as it lands, then settles on a spring (response 0.4, damping 0.6). A mark draws from its tip.
  • The glow. A box is a soft ring and halo that blooms and then settles. It stays 10 px outside the text, so it never cuts it.
  • The marker. A circle on a formula part or on words adds a wide marker stroke through the glyphs. Its blend mode comes from the surface under it: multiply on a light surface, screen on a dark one. A white figure in dark mode still uses multiply.
  • The chips. A label is a pastel chip with a coloured bar at its left, dark text in a sans font, and a thin leader line that ends in a dot on the part. Each label in a step has its own pastel. The chip pops in on a spring, and it never covers its target.
  • The strokes. Rings, underlines and sketches are perfect-freehand strokes with pressure, and they draw on as a pen does. An arrow is one light Rough.js stroke with a filled head. Marks from earlier steps fade to 45 %, and the glow of an earlier step goes.
  • The side panel. The example of Explain is a card on warm paper at the top right of the window, in a hand font, with the values in monospace. Each step adds its row: the circle on the value on the page at its word, the curve from it 120 ms later, the row when the curve lands, then each cell 80 ms after the one before. Rows stay for the next steps; their curves fade. A new beat (a new panel line) has its own title. While the panel shows, the page column moves left, so the panel never covers a mark. Below 1100 px the panel stands in the page, under the marked part.
  • The scroll. Before a step draws, the page scrolls its first mark into view when the mark is off screen or under the strip.
  • The voice. Each word of the spoken line in the strip lights up when it is said.
  • The state line. While the guide works, the strip shows one line: the wait text of the latest state event, a chip that says on this Mac or hosted · , the seconds after 3 s while the model writes, and Stop. Stop and Esc end the request, so the model stream closes. The caption of a board names its model, and has Voice off and Stop. The end shows what the guide saved, with Undo, and the hint line when the board counted as a hint on the open check.
  • The figure. The picture of a figure goes to the vision model only when the question is about it (the learner showed it, or the question names it), and the line says so first: “The guide sends this figure to to find its labels.”

With prefers-reduced-motion, the pointer jumps to its mark, and the marks and chips fade in for 150 ms. Text from the model goes in with textContent only.

Show while you talk

While the learner holds Hyper+E or types in the box, they can show the part they mean with the mouse. guide.js keeps the pointer path in memory only while the guide asks: page pixels, at most 30 points a second, the last 15 s and 600 points. The ask takes the path, finds the gestures, and forgets the path.

Gesture Rule
circle The path turns 300 degrees or more (and not more than 540) in 8 s, comes back near its start (20 px, or 35 % of the loop size), and its box is 24 px or more on each side
point The pointer stays inside 12 px for 400 ms or more, after it came from 40 px or more away. A rest at the end of a circle is part of the circle
nothing A small shake of a hand on the mouse, a swipe, a zigzag, an open arc, a small loop

A circle selects the anchors that it covers most. A point selects the smallest anchor that holds it. A gesture on no anchor gets the element with text under it as a new anchor. The ask sends at most 5 items, the latest first, as ctx.focus: {kind, box, anchors, t, words}. box is from 0 to 1000 of the first anchor, t is in ms from the start of the question, and words are the last words in the box near that time. The Mac overlay sends the same shape, with the same rules (tests/data/gesture_paths.json holds the sample paths that both test).

While the learner draws, a faint trail of the last 1.5 s shows in the board ink, and a soft ring shows on each circle or point for 1.5 s. With prefers-reduced-motion, there is no trail, and the ring does not move.

Demos

Interactive demos on the learning shelf: store them, make them in the background after repeated misses, and log each prediction.

A demo is one interactive figure from rupaka. It asks the learner for a prediction first. It shows the result after the learner locks in the prediction. This module keeps demos on the learning shelf. Concepts and attempts are on the same shelf. The module decides when the tutor makes a demo. It runs that job in the background, so the learner never waits.

rule what happens
a miss on a concept that has a demo the result of the question gets the demo, and the session shows it under the lesson
two misses with a saved misconception, or a concept with visual: true in its meta the tutor queues a job: a model writes a demo, and rupaka checks it
the learner asks (“Show me a demo” on the concept page) the same job starts immediately
a walk opens a step, and the next step has a demo or an order check the job for the next step starts, so its demo is ready in time
a prediction in a demo an attempt with kind='demo', and an answer to the learner model: depth 2, or depth 3 with a “why” line
the first miss after you saw a demo the lesson uses another way, and the demo stays next to it
the second miss after you saw a demo a simpler demo, or a job that makes one
the third miss after you saw a demo nothing new: the next question steps back to a prereq

Predictions

The demo page sends each prediction. record_prediction stores it as an attempt with kind='demo'. The attempt has the gate, the pick, the right answer and the “why” line. It counts the prediction in the stats of the demo. A prediction also shows what the learner understands. So it goes to the learner model as an answer. The depth is 2 (recall), or 3 (explain) when the learner wrote why. The rules are the same as for a question. A right pick with high confidence is solid. A wrong pick with high confidence is a misconception.

The misses since a demo

A prediction changes the count of the demo ladder (see below), so the count comes first. since_demo reads the count from your attempts, and rung gives it as a number. You saw a demo when a miss got a demo in its result (the attempt has shown_demo), or when you made a prediction in a demo. A wrong prediction counts as the first miss, because you saw the demo before it. more adds misses that are not saved yet.

Feedback on demos and lessons

Under each demo and each lesson, the app shows one quiet row: “Too simple · Just right · Not clear”. “Not clear” opens a short box for a note. The tutor keeps your choice as engine data, and uses it the next time:

  • on the attempt: feedback_on, verdict and note, and the list fb with each verdict on that attempt, so the history shows it;
  • on the demo: the counts of each verdict in stats, the last note, and the last feedback;
  • in the prompt of the next demo or lesson of the idea (demo.feedback and lesson.feedback);
  • on the ladder: “Too simple” skips the simpler demo, and “Not clear” brings it in earlier;
  • in the method model, with a small weight (see FEEDBACK in the method notebook);
  • in the profile: a “Not clear” note goes in “What confuses you”.

A verdict is one of three words. A note is learner text: clean_note removes control characters, keeps one line and cuts it at 500 characters.

Make a demo

make_demo asks the model for a demo with rupaka.author, and stores the demo. The loop validates the spec. It checks the spec in headless Chrome when a browser is available. It repairs the spec up to two times. When the model cannot make a good demo, make_demo returns None and stores nothing. The text lesson stays. When you said that the last demo of the idea was too simple or not clear, the prompt also has the line from feedback_line.

With aim='order', the demo is an order check. The prompt asks for one gate and one ranklist of 3 to 6 steps, and the examples are the gallery demos that have a ranklist. With aim='simpler', the prompt asks for a smaller demo of the core of the idea. The tutor uses it after a second miss that follows a demo. You can change both texts on the Settings page.

Each demo prompt also has the line IMAGES_LINE. It tells the model how to show an idea about images or noise: a field fn makes an n × n image from a formula, and a pixels block shows it. You can change this text on the Settings page too.

With said, the demo answers what the learner asked. The prompt adds the line ASKED_LINE and the words of the learner in quotes. The demo keeps asked: the key of the ask and its words.

The background job

queue_demo runs make_demo in the thread pool of the tutor. It runs only one job at a time for each concept and aim. A second call while the job runs gives the same job. The key of a job is the concept slug, or slug:aim for an aim. A job for an ask adds # and ask_key of the ask, so two asks on one concept are two jobs. job_state tells you if the job runs, failed or is done. job_age gives the seconds since the job started, so a page can stop the wait. Stop ends the job at the next try that fails the checks, or before the save; then job_state says stopped. The row keeps the inputs, so Do it again makes the same demo again.

Each job has a row in abhyasa.learner (job_key): the activity chip lists it, and the card of the demo loads again on its event. The said line of the row is the stage in STAGES, so the card changes when the model starts to write and when a try fails the checks. A try that fails the checks is a normal step, not an error: the tutor writes the demo again. _Tries logs the first 3 errors of each such try at INFO, with the key of the job, and keeps them on the row as tries, so the card can say why in a small fold. A job that starts by itself, such as the demo of a walk step or a simpler demo, is quiet: it has a row, but the chip does not list it.

The demo ladder

Sometimes you see a demo and still miss the idea. Then the tutor goes one rung down a short ladder. It counts only your misses on the idea since you last saw a demo of it. A pass ends the count.

misses since the demo what the tutor adds
1 a lesson in another way, from the method model: never demo, and never the way that just failed. The demo stays next to it.
2 a simpler demo (the aim simpler), or a job that makes one
3 or more nothing new. _back in the model sends the next question to the weakest prereq that is not learned.

The setting checks.demo_ladder turns the ladder off. Then a miss gets the plain demo, as before.

since_demo, rung and keep_rung (in the section on predictions) count the misses since the demo.

backed is true when _back sends the next question on the concept to a prereq. After a demo, that is after the third miss since the demo. From then on, the ladder starts no job. So the ladder and the step back do not pull two ways.

The tutor hook

on_close runs after each question closes (it is in CLOSE_HOOKS). A pass adds nothing. After a miss, it goes down the demo ladder when you saw a demo of the concept:

  • the first miss keeps the plain demo next to the lesson, which lesson_way wrote in another way;
  • the second miss gets a simpler demo, or demo_pending with demo_aim='simpler';
  • a later miss gets nothing new, and ladder in the result says which rung it is.

Your feedback on the demo changes two rungs. After “Too simple”, the second miss gets no simpler demo. After “Not clear”, the first miss already gets the simpler demo.

Else, it attaches the newest plain demo of the concept to the result, and marks the attempt with shown_demo. An order check or a simpler demo is not a plain demo, so on_close does not use it here. When there is no demo yet and the concept wants one, it queues the job. Then it marks the result with demo_pending.

Show me: a demo from your words

The learner can ask for a demo at any time: with the button “Show me” (⌥E) on a walk step or in a session, or with “show me …” in an answer box. The demo comes from what the learner asked, not only from the concept. So two asks on one concept give two demos.

This section has the parts that the app uses: show_ask reads an ask in an answer box, demo_kind picks the kind of demo, can_explain says if 3D explainers are ready, explainer_for makes a 3D explainer, and each ask is filed as a document, so the course can read it.

3D explainers

A 3D explainer is a rupaka spec with "mode": "learn" and one scene block. The scene has bodies, forces, labels and camera shots, and it builds in 3 to 6 steps, with one spoken line for each step. There is no gate, so the learner sees the thing at once. The learner gets one when they say “3D”, when the ask is about a physical thing, or when they click “Show it in 3D” under a 2D demo.

The model writes the spec. It never writes code. The prompt has the rules of an explainer, the manifests of the scene blocks from rupaka, and one good example. rupaka’s validate checks the spec, and the model gets one try to repair it. When the second spec also fails, abhyasa says so and shows the 2D demo.

The record of each ask

put_ask files one ask as a document of kind ask: the concept, the words of the learner (said, empty for the button), the text that the demo is made from (ask), its key, the kind, the place (where: walk, session, guide or concept) and where on that place (walk and step, or session). An ask never moves the learner model. A prediction in the demo of an ask keeps the id of the ask as asked, so asks can give the outcome.

An ask with no words and no open check has no key: its demo is the plain demo of the concept. asked gives one ask by its id.

An ask can have an aim: simpler for the simpler demo of the ladder. asks gives the asks, newest first, in the form of the course record: {id, at, where, said, ask, concept, slug, kind, outcome} and the place. slug is the demo of the ask, when it is made. For an ask of the kind explainer, it is the 3D explainer. outcome is right or wrong from the first prediction on the demo of the ask, else empty. The course reads this list. It can filter by concept, walk or session.

Talks

A walk as a talk for a group: the deck shape, its checks, a talk made from a walk, the run log and the recap.

A presenter can give a walk to a group. The talk is a list of slides. Each slide shows a part of the walk, one beat at a time, and it can have one question for the room. This module is the engine of a talk: the shape of a deck, the checks of that shape, the questions, a talk made from a walk, the store calls, the public deck that the room sees, the run log, and the recap after the talk. It imports no web code, so Leela can use the same shape and checks.

The imports are light: the standard library, the store, the walk paths (journey), the demos, the model calls, the prompts and the settings.

What a talk is

A talk is a document on the learning shelf, of kind talk. It points at its walk in src and copies what it shows, so a change to the talk never changes the walk. minutes is the slot of the presenter. phones is the choice “Room phones”. live is the id of the run that is open now, or None.

These names give the shape. A slide has one of SLIDE_KINDS, and a question has one of ASK_KINDS. A talk from a notebook (talk_from_sources) starts with a poll slide and ends with a next slide. A poll asks the room about itself, so its choice has no right answer. A next slide keeps the file:// link of the notebook in link.

Make it again

A walk can change after you make a talk from it: you add, remove, skip or move ideas, or change a note or a passage. “Make it again” brings these changes into the same talk, and keeps your edits. It matches a slide to a step by the concept slug, never by its place.

  • A slide whose idea is still in the walk keeps each part that you changed. A part that you did not change takes the new walk, when the step changed.
  • A new idea gets a new slide, at its place in the walk.
  • A slide that you added (a pause, questions, a primer) stays after the slide that it followed.
  • A slide whose idea left the walk moves, in its order, to the end, in the section “Not in the walk any more”.
  • An idea whose slide you removed stays out.

Your edits are the parts that changed since the talk was made. Each part of a slide as made has a short hash in marks. A part whose hash is not the same now is yours. (The history of the talk is not used for this: it keeps at most 50 changes, and a change of a passage or of more than one field names no field.) A talk made before 0.0.14 has no marks, so each of its slides stays as it is.

The handout

You send the handout to the room after the talk, as a PDF. handout_html writes one HTML file, and you save it as a PDF with Print in your browser.

Each slide with content is on its own page: an idea, a primer, a poll and the next slide. A pause, Questions and What we covered have no content, so the handout leaves them out. A question shows no answer on its page. The notebook and the sources come after the slides. The last section is “Answers”, so a reader can try each question first.

Fit a talk to its slot

fit_walk makes the hidden walk of a talk fit a slot of minutes, before the slides are written. It counts each step as its slide does (slide_minutes, with a question, and shown_step for a section of a notebook) and the closing slides, then skips steps from the end until the talk fits. The first step stays, so a talk always has one idea. A talk made again (talk_again) leaves the skipped steps out too.

fit_slides makes the slides of a talk fit its slot after they are written, and keeps each idea as long as it can. It first shortens: each idea slide takes at most 2 minutes, then the closing slides get shorter, then each idea slide shows only its points for 1 minute, with no question. Then it merges two neighbouring ideas into one slide. It cuts an idea only as the last step. A kept slide never changes. It gives the slides and the lines that say what it did.
