talk

A walk as a talk for a group: the deck shape, its checks, a talk made from a walk, the run log and the recap.

A presenter can give a walk to a group. The talk is a list of slides. Each slide shows a part of the walk, one beat at a time, and it can have one question for the room. This module is the engine of a talk: the shape of a deck, the checks of that shape, the questions, a talk made from a walk, the store calls, the public deck that the room sees, the run log, and the recap after the talk. It imports no web code, so Leela can use the same shape and checks.

The imports are light: the standard library, the store, the walk paths (journey), the demos, the model calls, the prompts and the settings.

What a talk is

A talk is a document on the learning shelf, of kind talk. It points at its walk in src and copies what it shows, so a change to the talk never changes the walk. minutes is the slot of the presenter. phones is the choice “Room phones”. live is the id of the run that is open now, or None.

These names give the shape. A slide has one of SLIDE_KINDS, and a question has one of ASK_KINDS.

Slides and beats

Each press of D shows one beat more. passage, body, figure and demo show a part of the slide. ask opens the question. body is a short list of points that the tutor writes for a slide that has no passage. lit:<text> lights a text in the passage, and lit:#<id> lights a part of the figure or the demo. Leela adds lines:a-b and out for its code slides.

A beat that shows a part needs that part on the slide. This table gives the part for each beat.

A figure is an image id, never a path or a URL: asset:<path in the vault assets>. An id with another scheme, a .. part, a leading /, a backslash, a second : or a control character is refused.

The body of a slide is a list of at most BODY_MOST points. Each point is a short text.

A list of short points is a good body. A text, or too many points, is not.

assert _body_ok([]) and _body_ok(['Scores become weights.'])
assert not any(map(_body_ok, ('Scores.', ['a'] * (BODY_MOST + 1), ['x' * (POINT_MOST + 1)], [1])))

A plain path and a path out of the assets folder are not image ids. A good id is.

assert _image_ok('asset:attention/images/fig2.png')
assert not any(_image_ok(f) for f in ('/Users/k/fig.png', 'asset:../vault.db', 'asset:/etc/x.png', 'ws:a.png', 'asset:a:b.png', 'asset:a\\b.png', 'asset:a\nb.png', None))

_ask_problems checks the question of one slide. A choice needs 2 to 6 options and the index of one of them. An order needs the indexes of all its options, each one time. A run question (“What does this print?”) has 2 to 6 options or none, and no answer before the run.

_beat_problems checks the beats of one slide against what the slide shows.

A text field that you write can hold no control mark and no direction mark (CTRL of abhyasa.edit): a mark can hide text or turn it around on the screen. clean_slide strips them from the fields of a slide, and check_talk refuses a slide that still has one. A passage is the word-for-word text of a source, so it stays as it is.

Questions for the room

A demo gate with fixed options can be a room question with no model call. ask_from_gate and public_ask are thin wrappers over rupaka.poll.of_gate and rupaka.poll.public, so the rules come from rupaka. The options are a list, or {"from": path} in the state of the spec. The answer is {"is": value}, or a path in the state. A path that is not in the state (it needs derive) gives None, and so do fewer than 2 or more than 6 options. The prompt and the options are written as the drawn gate shows them, so the room reads the same text as the demo on the screen: 2.0 shows as 2, a minus is the sign −, a number has at most 4 digits after the point (or the digits that a {path:2} field gives), and None shows as empty.

ask_from_gate gives a choice from gate gate of spec, or None.

A short check becomes a choice of 4 options through one model call, with the prompt talk.choice. The answer stays in the talk. When the call fails, or the reply is bad, the question is a words question.

_choice gives the reply as a choice when it has a question, 4 different options and the index of one of them, else None.

When there is no choice question, the slide asks for a short answer in words. words_q writes it from the name of the idea, and never changes the case of the name. A name that reads as a question (it ends with ?, or it starts with Why, How, What, When or Which and has more words) is the question. Any other name goes in quotes after “what is”, so a name such as “CAN bus” reads well. An empty name gives no question (None).

A talk from a walk

Each walk step that is not skipped gives one idea slide. A demo or an order check takes its question from the first gate of the demo that can be a room question. A step with no demo, or with no such gate, uses its passage and a short check. A code check gives a words question, because a talk never runs code.

_idea_ask gives the demo slug (or None) and the question of one step.

_idea makes the slide of one step. Its beats show the passage, then the figure, then the demo, each when the slide has it. The slide keeps the source of its passage, so the editor, the room and the recap file can name it.

What the slides say

A walk from a paper or a link gives each slide a passage. A walk from a topic does not: its steps have no passage, and the tutor note of a step comes only when a learner opens the step. So the tutor writes the content of each slide when the talk is made. A slide with no passage gets 2 to 4 points for the room. Each slide with no speaker note gets one: what to say, one question to ask the room, and one common confusion to watch for. A slide with a passage keeps it, and gets only the notes.

The prompt talk.slide asks for both, with one model call for each slide. You can change it on the Settings page.

_body gives the reply as points and notes, or None when it is bad. slide_notes writes the notes as Markdown.

Make it again

A walk can change after you make a talk from it: you add, remove, skip or move ideas, or change a note or a passage. “Make it again” brings these changes into the same talk, and keeps your edits. It matches a slide to a step by the concept slug, never by its place.

  • A slide whose idea is still in the walk keeps each part that you changed. A part that you did not change takes the new walk, when the step changed.
  • A new idea gets a new slide, at its place in the walk.
  • A slide that you added (a pause, questions, a primer) stays after the slide that it followed.
  • A slide whose idea left the walk moves, in its order, to the end, in the section “Not in the walk any more”.
  • An idea whose slide you removed stays out.

Your edits are the parts that changed since the talk was made. Each part of a slide as made has a short hash in marks. A part whose hash is not the same now is yours. (The history of the talk is not used for this: it keeps at most 50 changes, and a change of a passage or of more than one field names no field.) A talk made before 0.0.14 has no marks, so each of its slides stays as it is.

What the room sees

The room sees a public deck. It is made from a list of allowed fields, never by removing fields, so a new field in a talk does not reach the room. It has no notes, no answers, no source of a question, no demo and no path. A figure comes by the sha256 of its bytes.

Only png, jpeg, gif and webp files can be figures. image_type finds the type from the first bytes of the file, not from its name.

The run log

Each time the presenter gives the talk, a run log keeps what happened: the place, the time on each slide, the rounds of each question, the hands, the questions from the room that the presenter kept, and the primers that were opened beside a slide. It keeps counts only. It keeps no device token, no address and no answer of one person.

new_run starts a run on the first idea slide. key is a random 64-bit value. The channel name of the two windows has it, so an old window never drives a new run.

The data of the recap of run of talk t; names gives the name of the idea of each primer.

The recap file is one HTML file for the room. It needs no server: the style is inline, with the token names of the themes and the light values of Paper, and the figures are data: URLs. It has no script, no speaker notes and no names. All text goes through html.escape, so text from the room stays text.

_ask_html draws one question: the options with the right one marked, the share right of each round, the hands, and the words answers that the presenter showed.

recap_html gives the file. A slide that a run showed and that is parked now is left out: the title and the date, then each shown slide with its title, passage, figure, question and result, and the question of each primer beside it, then the questions from the room that the presenter kept, with the notes, and at the end the sources. The slides come from the public deck, so the file can not show more than the room saw, apart from the right answers.
