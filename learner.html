learner

The learner and the shelf: the settings, the prompts, the store, what you know, how you learn, the jobs and the stored walks.

This module is the base of the engine. Every other module imports from it, and it imports from no other module of abhyasa. It holds what abhyasa knows about the learner, and the shelf where it keeps it. The parts come in the order that they import each other:

  • Settings: the settings file, the settings table and its defaults.
  • Prompts: the system prompts that you can see and change in Settings.
  • The store: the learning shelf in your vault. Each concept, attempt and session is one document.
  • The learner model: the depth, the floor and the ceiling of each concept, and when to review it.
  • Ways to learn: which way of teaching helps you, such as code or an analogy.
  • The profile: your background, goals, interests and pace.
  • Background jobs: the stored rows of the jobs that the activity chip shows.
  • Stored walks: read and save a walk, find its current idea, and count its steps.

Two functions of the profile ask a model. They import the model layer (abhyasa.models) when they run, because that layer imports this module.

Import the modules that this module uses. The heavy ones load inside the functions that need them, so the import stays light.

Settings

One table for each value that you can change, and the file that keeps your changes.

Each value that a person can change is a row in one table, SETTINGS. A row has a group, a name, a label, one line of help, a type, a default and, for a number, a range. The engine, the web app and the Settings page all read this table. Thus each value has one place.

Your changes go in settings.json in cfg_dir(). The code reads a value when it uses it, so a change works at once, with no restart. A saved value outside its range gets the nearest end of the range. A saved value of the wrong type gets the default. A bad file never stops the app.

This module imports only the standard library and fastcore. Each engine module reads its values from here, so the import must stay light.

The groups

The Settings page shows the groups in this order. Each group has a label and one lead line.

The table

add puts one row in SETTINGS. The name is section.key: the section of settings.json and the key in it. The type comes from the default. more puts the row under the closed “More” part of its group. store='profile' marks a value that the vault keeps in your profile, not this file. hi can be the name of another row. Then that value is the top of the range. ui=False marks a value that its group shows with its own controls. reset=False keeps a value when you use the defaults of its group: the theme, and the speech engine and model.

The Look group keeps its own controls: the theme swatches and the mode. The Learning group holds the three values of your profile.

The Walks group sets the size of a walk and of a side walk.

The Talks group sets how a talk runs: the questions, the time, the vote and the room.

The Checks and grading group sets the tries, the grade of a shaky pass, and when an idea counts as learned.

The Review group sets the time to the next review. A daily limit on review is new: 0 means no limit, as before.

The Links group sets how much of a link the tutor gets. The pages read by default can not be more than the page cap.

The Research group sets the web search for a step with no source. The tutor searches the web for the idea, reads the best pages, and quotes one passage word for word. When research is off, the tutor does no web search, and the step says that the text is in the tutor’s words.

The Speech to text group keeps the engine and the model, and the pauses at which the mic cuts what you say. The Screen guide group has the voice and the look of a point mark. A point mark is weaker than a circle in each look, so a circle is always the main mark of a step. The default is tick, because it has no ring that looks like a circle.

The Speaking voice group picks who reads the steps of the screen guide aloud. pocket runs Pocket TTS on this Mac. openai sends each line to OpenAI. browser is the voice of the browser (or of the Mac in the overlay). The voice module reads these values. The default is pocket. Until its model is downloaded, the browser speaks. An old hf or kokoro value is not one of the choices, so it reads as pocket. The speed is only for OpenAI: Pocket TTS has no speed.

The Models group has the default model and one model for each task. An empty value uses the default model. The tasks after extract borrow the model of an older task when they have none: BORROWS says which. The screen guide (guide) and its figure labels (guide_vision) use the model for hints until you pick one. The builder chat (build) is an agent: it uses the default model until you pick one, and it has no reply cap. The reply caps are in tokens.

The Lists group sets how many items show in the lists of the app. All of it is under “More”.

Each group except Prompts has rows, and each row is in a group. The Prompts group lists the prompts of prompts.PROMPTS.

assert set(GROUPS) - {'prompts'} == {r.group for r in SETTINGS.values()}
assert all(r.kind != 'int' or r.lo <= r.dflt for r in SETTINGS.values())

What stays fixed

Some values keep you safe, so they have no setting: the link checks for local addresses, plain HTTP, the link kinds, the HTML allowlist, the check of a pane address, the local-only hosts, the test allowlist, the grade scale and the depth ladder. The room for phones keeps its safety limits fixed too: the bind rule, the join code, the rate limits, the body size and the headers. FIXED names them, and no row may have one of these words in its name.

Prompts

The instruction text of the tutor. You can change it on the Settings page.

Each prompt of the tutor has two parts. The variable parts (the concept, the thread, the JSON shape) stay in code. The instruction text is in this registry. Each prompt has a name, a plain label, a note on what it changes, and its default text from code. The Settings page shows each prompt, and you can change its text there. The tutor reads each prompt when it calls the model. Thus a change works on the next question, with no restart.

Import the tools that this module uses. The settings come from settings only when a prompt is read, so the import stays light.

Write concepts

put adds a concept or adds to it. It keeps the learner state, merges the list fields and replaces the other fields. It does not change the group of a concept that the learner moved by hand (see Groups below). Two fields say what the learner must understand. core is the understanding in 1 or 2 sentences: what the idea does and why. It has no sizes, years or scores, unless the number is the idea. wrong lists 1 to 3 common wrong ideas, each as {'think': ..., 'fact': ...}. The question and the grade work from these two fields. statement stays as the reference text. An empty core or wrong keeps the old value. wrong_ideas makes each wrong idea a dict. clean_name makes a name one line with no control characters, at most NAME_LEN characters. put and rename use it.

The learner model

The learner model: how deep you know each concept, when to review it, and what to ask next.

This module holds the learner model as plain functions with no model calls and no storage. It finds what an answer means, updates the state of a concept, finds the next depth and picks the next concept. The tutor calls these functions and the store keeps their results.

Import the tools that this module uses.

Depth

Each concept has a depth from 0 to 5. The tutor asks each question at one depth.

depth name a question at this depth asks you to
0 unseen (no question)
1 recognise pick the correct statement from options
2 recall state the idea or the rule
3 explain say why it is true, in your own words
4 apply use it to solve a problem
5 transfer use it in a new case or link it to another subject

The floor is the highest depth that you pass reliably. The ceiling is the lowest depth that you failed (6 until you fail). The next question goes between them. Thus each answer moves one edge of this range.

These constants name the depths, give the question kind at each depth, and set the goal and the high-confidence line.

Outcome

Correctness and confidence together tell what an answer means.

high confidence low confidence
correct solid fragile
wrong misconception gap

“I don’t know” is a gap. A correct answer that used two or more hints is fragile.

Memory

Recall falls with time as in FSRS: \(R(t) = (1 + \frac{19}{81}\frac{t}{S})^{-1/2}\). The time \(t\) and the stability \(S\) are in days. At \(t = S\), recall is 90%. Thus the due date is the last review plus \(S\) days.

recall gives the recall now. grow gives the new stability after an outcome.

Ways to learn

The ways you learn: six text ways (code, maths, analogies, worked examples, diagrams and plain words), and demos, ordering, playgrounds, boards and timelines. This module finds which ways work for you, and when to try a new one.

Each question, hint and lesson uses one way to teach: its method. The tutor picks the method before it writes the prompt. So the tag is known, not guessed. When a question closes, its outcome counts for its method: solid 1, shaky 0.5, a miss 0.

The counts give each method a Beta posterior, for each subject and over all subjects. choose uses them in two ways:

  • Drill: a weak concept gets your best method.
  • Explore: a concept that is not weak sometimes gets another method. You set the chance (explore in the profile). First choose tries a method that got better recently. Else it uses a random draw (a Thompson sample).

The counts are in one stats document on the shelf. This document is only a cache: method_stats builds it again from the attempts.

The methods

METHODS maps each method to the line that the prompt gets. EXAMPLES_TO maps the profile’s “examples that help” to methods, to set the prior.

Feedback counts a little

The row under a demo or a lesson also counts for the way of that demo or lesson, with a small weight from FEEDBACK. “Not clear” adds 0.25 of a miss, so four of them count as one miss, and one click does not decide the way. “Just right” adds 0.1 of a pass. “Too simple” adds nothing: the way worked, but the step was too small. The way for a check

check_for picks the way for one check of one idea. It looks only at the ways of the idea that a walk can show. It does not repeat the way of the last check when it has another. The kind of the check follows the way, and the depth follows the kind. A short check is depth 3 or more: it asks for the idea and why it holds, never for a fact to recall. It is depth 4 when the floor is 3 or more.

A hands-on way of the idea (a key of CHECK_KIND: demo, order or code) comes before its text ways. The model lists a hands-on way only for an idea that fits it: a process, a sequence, or code. A code check is a notebook that runs in Leela. Without this rule, the learner stats and the profile pick a text way almost every time, because the profile names only text ways. Then nearly every check is a short answer.

Only the idea’s own ways can give a hands-on check. An idea with no way that a walk can show gets a short answer in a text way. A walk passes hands=False when it has its share of hands-on checks (see hands_most in journey).

The profile

What abhyasa knows about you: your background, goals, interests, the examples that help you, your pace, and what confuses you.

The tutor asks better questions when it knows the learner. A coder gets code examples. A Sanskrit reader gets a Sanskrit example. This module keeps one profile document on the learning shelf. The profile gets data in three ways: a short first conversation, edits by the learner, and changes that the tutor makes from evidence. The module keeps each change with who made it and why. So the learner can see each change and undo it. The profile stays in the vault on this machine.

Who the words are for

Each text that explains an idea is for a human, and humans differ. One learner is new to the idea, and another knows it well. A text that only says the definition again teaches little to both. So each teaching prompt gets two more parts:

  • teach.human, one shared prompt with the rules on how to teach. It comes from the research on how people learn: adapt to the level (the expertise reversal effect), a concrete case before the abstract rule (concreteness fading), worked steps for a new learner, an analogy with its limits, the reason why, and the common wrong idea.
  • level_line, one short line on how well this learner knows the idea now. It comes from the learner model: the state of the idea (understanding), the reasons it is weak, the needs that are not in place, and the profile.

The rules say what to do for each level. Shaky, a gap or a missing need: keep it simple, one idea at a time, a concrete case first, step by step. Solid: be short, with the exact terms and fewer worked steps.

How well you know what you know

A good learner knows what they know. When you feel sure and you are often wrong, you stop checking your own thinking. When you feel unsure and you are often right, you hold back ideas that work. The “Sure?” choice on each answer gives the data. calibration counts the first try of each question. It counts how many times you felt sure (60% or more), and how many of those answers were right. It counts the same for unsure. An answer with no confidence, a “don’t know” and a demo do not count.

Background jobs

One stored row for each background job: what runs, what ended, and where to see it. The activity chip, the event stream and the Mac app read these rows.

abhyasa does slow work in the background: it looks for sources, makes a walk from a link or a goal, files a folder, plans a course, and writes the notebook of a step. Each such job has one row here. A row has a kind, a state (running, done, failed, stopped or closed), a said line, the start and end times, a title, and a url: the page of its object.

The rows are in vishalakshi’s job Ledger (Vault.ledger), a table in the vault file, so they survive a restart. This module is thin glue over it, with the names that the blocks use. The pool future of a job stays in memory; the row is the truth for the pages. At a start, each row that still says running becomes closed: no job lives across a restart.

Each running job has Stop. Stop asks the job to end at its next safe point, and the job ends as “You stopped it.” A job that keeps its inputs on its row (again) has Do it again when it ended: the block that runs it starts the same job with the same inputs.

The rows live in the vault file, next to the concepts and the walks.

The row

ENDED are the states of a job that does not run. FRESH is how long an ended job shows in the activity chip, until you open its page. KEEP is how long an ended row stays at all: the ledger deletes it at the next start of a job.

abhyasa 0.0.15 kept all the rows in the meta of one document (abhyasa:jobs:all). The first read of the ledger moves those rows to it one time, and forgets the document. A row that said running is closed, as its job did not live across the restart. A row that abhyasa cannot read is left out: an old row never stops the app.

Change a step, read the rail

walk_step merges changes into one step and saves the walk. merge_journey merges changes into the fields of the walk, such as sitting. Both hold the lock of the walk (keyed_lock, one lock for each kind and key), so two requests on one walk do not lose a change. walk_state gives each step a dot for the rail: done (outcome solid), shaky (outcome fragile, gap or misconception), skipped, known, now (the first step with no outcome and the status todo) or todo.
