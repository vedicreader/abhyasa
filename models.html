models

The models: the model for each task, the PII guard for the text that leaves the Mac, and speech.

This module holds the models that abhyasa talks to. It imports only from abhyasa.learner. It has three parts:

  • The model for each task: the route of each task (for_task), the default ask (route_ask), the list of models, and where each one runs.
  • The guard: ramabana’s PII guard. Text that leaves the Mac passes it first.
  • Speech: speech to text and text to speech, on this Mac or with OpenAI.

The heavy model code (ramabana, rishi, mlx-audio) loads inside the functions that use it, so the import of this module stays light.

def parse_json(

Fake

def Fake(
    rules:dict=None, dflt:str='{}'
):

A stand-in model for tests: Fake({'grade': {...}, 'question': {...}}).

A matching rule gives its reply, and Fake records the call.

f = Fake({'GRADE': dict(correct=True)})
test_eq(ask_json(f, 'GRADE this'), dict(correct=True))
test_eq(len(f.calls), 1)

After a reply that is not JSON, ask_json asks again and gets the JSON.

bad = Fake(dict(X=lambda p, sp: 'oops' if 'not valid' not in p else '{"ok": 1}'))
test_eq(ask_json(bad, 'X'), {'ok': 1})

With need, a reply must be one JSON object with text in each of those keys. A list, or an object with no question, gets one more try. A second bad reply raises a ValueError that names the key.

odd = Fake(dict(Q=lambda p, sp: '{"question": "What is a rank?"}' if 'must be one JSON object' in p else '[1, 2]'))
test_eq(ask_json(odd, 'Q', need=('question',)), {'question': 'What is a rank?'})
test_fail(lambda: ask_json(Fake(dflt={}), 'Q', need=('question',)), contains='question')

A model for each task

The tutor does five tasks, and each task can use its own model. A quick model can grade and give hints. A strong model can write questions and lessons. The Settings page saves the choice. Router reads it on each call, so a change has an effect on the next call.

task what the model does
question writes a question and its hidden model answer
grade reads the conversation and grades it
hint gives the next hint
lesson teaches the smallest step after a miss
extract finds the concepts in a text

Each task also has a reply cap: the most tokens that the model can write in one reply. TOKENS gives the default of each task. A question has options and a rubric, and an extract can name 15 concepts, so these two get the most. A hint is short. The Settings page can change each cap. Only the cap is a setting, because ramabana’s oneshot uses no other per-call value: it turns thinking off, and the time limit of a model is in ramabana’s config.toml. The model layer gives the cap to the API models (OpenAI, Codex, Gemini, Copilot) and to the models on this Mac. Claude Code does not use it for the reply, but ramabana uses it to fit the prompt in the window of the model.

model_ask gives an ask for any model name. The name can be any model that ramabana can run: Claude Code, Codex, OpenAI, Copilot, Gemini, or a model on this machine (LiteRT, mlx, llama.cpp, Ollama). The call goes through the routing of ramabana, as route_ask below shows.

Names for the model list

The Settings page shows a list of models. Each item has a name that people know, such as “Claude Sonnet” or “GPT-5.5”. The model id, such as claude/sonnet, is the value that the settings keep. ramabana’s model_label makes the name from the id, and model_label here adds “a local model:” before the name of a model that runs on this Mac. PROVIDERS gives the name of each group in the list, and provider_label reads it. ramabana’s is_local tells if a model runs on this Mac. For Ollama, it looks at the daemon host (the host in config.toml, else $OLLAMA_HOST), and it does not connect to it. Thus a model on an Ollama daemon on another computer has no “a local model” name, and its group is “Ollama on another computer”.

catalog lists the models that can run here, for the Settings page: the rows of ramabana’s available_models(ttl=). Each row has a name from ramabana’s model_label, local, vendor and model_id. abhyasa adds “a local model:” before the name of a local row. The look-up asks each provider, so it takes some seconds. ramabana keeps the list in memory and on the disk: a new process shows the last list at once, and a list older than ttl seconds refreshes in the background. When the look-up fails, the list has only the models in FALLBACK.

catalog

def catalog(
    ttl:float=300.0

The models that can run here: ramabana’s rows (value, name, label, provider, source, local, vendor, model_id), with LOCAL before the name of a local row. The last list comes at once; one older than ttl seconds refreshes in the background.

These tests use ramabana. slow is a stand-in for the slow look-up of ramabana (_model_rows): it counts its calls, and gives one row with the facts of ramabana (_facts). The tests keep the list in a temp folder.

import ramabana.core as rc

Two calls to catalog ask the providers one time.

calls, real, real_dir = [], rc._model_rows, rc.PROBE_DIR
def slow(include_legacy=False): calls.append(1); time.sleep(.5); return [rc._facts(dict(value='claude/sonnet', label='sonnet', provider='claude', source='login'))]
rc._model_rows, rc.PROBE_DIR = slow, Path(tempfile.mkdtemp())
rc.forget_probes()
test_eq([r['name'] for r in catalog()], ['Claude Sonnet'])
test_eq((catalog(), len(calls))[1], 1)

A new process has no list in memory. It gets the last list from the disk at once, with no slow call, and a refresh starts in the background.

rc.forget_probes()   # the memory copy goes, as in a new process; the disk copy stays
t = time.time(); rows = catalog()
assert time.time() - t < .3 and [r['name'] for r in rows] == ['Claude Sonnet']
for _ in range(50):
    if len(calls) == 2: break
    time.sleep(.05)
test_eq(len(calls), 2)

Every call through ramabana

ramabana is the agent layer on top of the model layer. Its Routing sends each job to a model. When a cloud model fails or gives no answer, Routing puts it aside for five minutes and sends the job to the next route: other cloud models, then a small model on this Mac. Its backends stay open, so a call does not pay the start time of a new Chat.

ramabana_agent makes one ramabana Agent for the process, on the first call. The Agent gets only what Agent.oneshot needs:

  • NullHost: no folders, and each file operation is refused.
  • readonly=True, no sub-agents, no extensions, no skills, no lessons: no tool can write, run code or go on the network.
  • Approvals that refuse when nobody answers, and no saved rules.
  • cfg=None: no history, plan or run log, so the Agent writes no files.
  • A short briefing, so that it does not read skills or project files.

The turn of the Agent is the default model, so a task whose model fails goes to the default model first.

ramabana_agent

def ramabana_agent(
    turn:str=None
):

The one ramabana Agent of this process, made on first use by ramabana’s model_agent on the turn dflt_model(turn): no folders, no tool that acts, no files.

Each task is a ramabana job with the same name. _point sets the model of the job before each call, only when the settings changed it. A model that ramabana put aside stays aside until its time is up.

ramabana_oneshot asks one question on the job of a task, through ramabana’s Agent.oneshot with wait=True and strict=True. With wait, a call waits for a backend that another call holds, on the first route and on each fallback. With strict, a call that no route answers raises ramabana’s OneshotEmpty, with the routes that ramabana put aside or the note of the route.

A failure can take some time: ramabana tries each route in turn, then the small model on this Mac. It puts a failed cloud model aside for five minutes.

A route can also raise ramabana’s OneshotTimeout when a call goes past its deadline. no_answer changes each of the two errors into one RuntimeError that names the task, the model and why, so each caller catches one kind of error.

prepare lets the caller change the text for each route, as ramabana’s Agent.oneshot does. The guide uses it for its guard: the guard then knows if the model of the route is on this Mac. HOSTED is the model that a guard takes when it does not know the route.

The worker agent

ramabana_worker makes a second ramabana Agent, for the gather agent of research. It is never the one Agent of ramabana_agent, so a long gather never holds a one-shot call. It runs on the default routing (Routing(turn=dflt_model())). Its host is the shalya host (default: a NullHost, with no folders). The caller names its tools in tools, then adds them with add_tool. ramabana’s only_tools offers the model only those tools, and refuses a tool with another name. ramabana’s memory and plan tools are held back. It has no approvals listener, so a tool that writes is refused. The caps stop a turn after max_calls tool calls, max_steps model steps, max_tokens tokens or max_cost dollars. A model such as Claude Code on a plan reports no cost. Then ramabana estimates the dollars from the tokens at the price of the model (ramabana.agent.token_rate), and keeps the estimate in estimated, so the dollar cap still holds.

The guard

Text that leaves the Mac passes the PII guard first.

Text that leaves the Mac passes ramabana’s guard (ramabana.guard) first. guard(s, model) is for a model call: the page context and the question, and the prompt of a vision call. It is outgoing for the model of the route. It always masks API keys, tokens and private keys as [SECRET]. For personal data it follows ramabana’s setting cli.pii, but only for a hosted model: redact masks it, refuse withholds the text (Withheld), and off lets it through. A model on this Mac gets the personal data. When the route is not known, guard takes a hosted model (HOSTED).

safe_query(q) is for a web query. It is ramabana’s query: a query with a secret or with personal data does not go, with any setting.

The guard reads text only. A figure image goes to the vision model as it is: no text guard can read pixels.

Speech

Speech to text on this machine, for think-aloud answers, and a natural voice that reads the guide aloud.

This module turns a spoken answer into text. With the local engines, the audio does not go off the machine. The web app records while you talk. It cuts the audio into segments at your pauses and sends each segment here. This module transcribes the segments one at a time, in order. The text goes into the think-aloud box while you continue to talk.

The module also speaks. speak turns one line of the screen guide into WAV audio, with the start time of each word, so the board can light each word as it is said.

These are the imports of the module.

Engines

There are two engines. mlx runs on this machine. openai sends the audio to OpenAI.

  • mlx runs any speech to text model that mlx-audio can load. The default is Qwen3-ASR 0.6B (8 bit, 1.0 GB). Whisper large-v3-turbo is the second model on the Settings page, and the search finds the others. Install mlx-audio with pip install abhyasa[whisper].
  • openai uses the OpenAI transcription API. It is off until you set a key. It sends the audio off the machine.

Each engine gets a hint: the name of the concept and its terms. Qwen3-ASR reads it as hot words, Whisper as its initial prompt, and OpenAI as its prompt.

A gap at the end

A local voice ends its line with no gap. On a Bluetooth or AirPlay output the last part of the sound is still in the buffer when the page stops the audio at its ended event, so the line seems to stop too soon. pad_wav fades out the last PAD.fade seconds and adds PAD.tail seconds of silence after the line, and PAD.lead seconds before it, for an output that wakes up late. A voice reads $ym$ as “yum”, and \alpha as “backslash alpha”. spoken puts the maths of a line into words before any voice says it: $…$, $$…$$, \(…\), \[…\], a short name in back quotes, and a bare W_Q (one letter with a short subscript). tex_words reads a run of single letters letter by letter, a Greek letter by its name, the common operators, ^2 as “squared”, _m as “sub m”, \frac, \sqrt, \bar and \hat. One worker for the voice

Speaker has one worker thread for all the calls of the speaking voice, separate from the speech to text worker. Thus a line of the board does not wait for a segment of dictation. It keeps the lines that it said in this run (at most most), by engine, model, voice, speed and text. The board asks for the same line again when the learner goes back a step, and that line then comes at once. Two requests for the same line share one call. warm loads the model in use with one short line, so the first line of a board does not wait for the load. The browser voice and OpenAI have nothing to load.

A model that is not on this Mac yet is not downloaded for a line: the Settings page shows its download. Until then, say refuses the line with the word “browser”, as for the browser voice, so the page and the Mac app speak with their own voice.

When the voice fails on a line, error keeps why, as one plain line, so the Settings page can show it under the choice. The next line that the voice says clears it.

Segments in order

The browser sends one segment each time you stop to think. Speech has one worker thread for all the model calls. Thus only one model is in memory, and the segments run one at a time, in the order they came. A Dictation collects the segments of one answer. next gives the text in the order of the segment numbers, also when a slow request arrives late. When the browser sends a segment again (after an error), the code does not use it two times.
